## 性能优化 P1 收尾（接 10-12 的 P0）

**P1-D 流式 markdown 渲染节流**（新文件 `packages/ui/src/lib/streamingMarkdownThrottle.ts` + `packages/ui/src/hooks/useStreamingTextThrottle.ts`，集成于 `message.tsx` MessageResponse）
- 实锤：streamdown 内部块解析（Lexer+remend）无 memoization（查过 dist 产物），流式每 chunk 全文重解析。
- 方案：80ms 节流（~12.5fps）流式文本进入解析管线；leading+trailing 语义，settle 兜底尾帧不丢；完成态旁路。
- 决策核心框架无关（显式时钟、纯同步），hook 只做定时器适配——测试无需 React 基建。
- 测试 `streamingMarkdownThrottle.test.ts` 5/5（含 300 轮随机差分）。

**P1-E 工具长输出默认预算**（`contracts/tools/contract.ts` + `core/src/tool/executor/result-serialization.ts` + `result-content-projection.ts`）
- 实锤：默认预算（MCP 等未声明工具）100KB head-only 截断；bash 已是 artifact+tail 不用动。
- 方案：默认改 artifact 策略（落盘+2KB envelope，artifactStore 缺失优雅回退）+ 新增 `head-tail` 截断方向（head 70% + 省略标记 + tail 30%，字节严格 ≤ 预算，marker 含精确省略字节数）。
- 显式声明 resultBudget 的工具逐字节不变。测试 `resultHeadTailTruncation.test.ts` 4/4（80 轮随机差分）。
- 坑：测试生成器逐步 `Buffer.byteLength` 是 O(n²)、`fitStringToBytes` 二分在 200KB 串上反复分配 Array.from——300 轮直接跑挂（SIGTERM）；优化为指数回退测量 + 40KB×80 轮后秒级。

**P1-F message-history 深拷贝——实测后跳过**

- 原始怀疑不成立，按实测文化记录跳过，不做结构共享重构。

验证：`pnpm typecheck` ✓、`pnpm lint` 0 errors（70 警告全为基线，改动文件零新增）✓、`pnpm architecture:check --changed` 0 violations ✓。

## P2 收尾（同日下午）

**P2-A mermaid 懒加载**（新文件 `packages/ui/src/lib/lazyMermaidPlugin.ts`，改 message.tsx / mermaid-block.tsx）
- 基线实测：web 生产 entry chunk 5.66MB（gzip 1.67MB）单文件；shiki 语法包本就正确按需分块（各语言独立 chunk），svg 无 barrel，均无需处理。
- A/B 实测：mermaid 移出静态图后 entry 5.66→5.63MB。**重要发现：mermaid v11 内部本就按需动态加载图表模块，静态成本只有约 30-90KB，远小于"数百 KB"的原始估计**。改动仍保留（明确异步边界 + 语义等价），但收益有限。
- 两个关键坑：
  1. verbatimModuleSyntax 下 `import { type X } from "pkg"` 会残留成 side-effect import 把包拖回静态图；必须用 `type X = import("pkg").T` 类型位置语法（编译期整体擦除）。
  2. `@streamdown/mermaid` 导出的 `mermaid` 是插件对象不是实例，要经 `getMermaid(config)` 取实例。
- spec：`specs/startup-lazy-mermaid.md`。
