## 约束

三组可以，但同一文件只能出现在一组里。

## 归属规则（唯一一条，保证不重叠）

**文件有已暂存内容 → 只进「已暂存的更改」**（即使它同时还有未暂存的修改）；否则有未暂存改动 → 「更改」；否则 → 「未进行版本管理的文件」。

| 组 | 行内显示 | 提交模式 |
| --- | --- | --- |
| 已暂存的更改 | 索引里的增删行数 | 不 `git add`，只提交索引内容 |
| 更改 | 未暂存的增删行数 | `git add` 后提交工作区内容 |
| 未进行版本管理的文件 | 同上 | `git add` 后提交 |

```
✓  提交文件
›  ✓  已暂存的更改                    2 个文件
       ✓  A.java  另有未暂存改动  +3 -0
›  ✓  更改                           14 个文件
       ✓  B.java             +7 -0
›  ✓  未进行版本管理的文件             15 个文件
       ✓  C.txt              +1 -0
```

「另有未暂存改动」是纯文字提示（不是第二个勾选框），说明该文件本次只提交已暂存那半段；可去掉。

## 提交语义

- `worktreePaths` = 勾选的「更改」/「未跟踪」行
- `indexModePaths` = 勾选的「已暂存的更改」行中**还有未暂存余量**的
- `stagedOnly = worktreePaths.length === 0 || indexModePaths.length > 0`
- 没有部分暂存时 → 普通分支，**与今天默认代码路径完全相同**；清单只有已暂存行时 → `stagedOnly: true`，与今天"自动关掉开关"一致。

## 两条行为变化（需确认，因为动了 spec 规则 1）

1. 部分暂存文件的默认行为：今天整份工作区内容被提交（`git add` 把未暂存半段也带上）；新模型只提交索引那半段，余量留在工作区（`git commit` 原生语义，也让 `git add -p` 真正生效）。
2. 它的未暂存余量不出现在清单里（否则违反约束），页头 `+/-` 对这类文件只算已暂存部分，靠「另有未暂存改动」提示。

**不暂存任何东西的用户（当前仓库状态）感知不到变化**：已暂存的更改为空组不渲染 → 只剩更改 + 未跟踪，全部勾选、`git add` 全部、一次提交全部，与今天逐字节相同。

## 唯一协议改动

`GitGenerateCommitMessageRequest` 加 `stagedPaths?: string[]`（= `indexModePaths`）。消费点 `gitService.ts:150` 的 `getCommitMessageDiffQueries` 与 `generateCommitMessage` 的 `files` 过滤：这些路径只取已暂存 diff，否则消息会描述并未提交的未暂存余量（违反 spec 规则 7）。`includeUnstaged` 保留，弹窗恒发 `true`。

## 风险

1. 部分暂存文件的行为变化是有意的，但确实与 spec 规则 1 的"逐字节一致"冲突，需在 spec 里改成明确口径。
2. 混合模式依赖既有 plumbing"按真实 index 逐个 `update-index --cacheinfo`"的实现（含 rename 的 `originalPath` 清理）。
3. 冲突条目无 staged 记录 → 落「更改」组，与今天一致；默认路径本就先 `git add`，失败模式不变。
4. 跨版本 remote host：`stagedPaths` 为新增可选字段，旧 host 忽略 → 消息可能多描述未暂存余量（可降级），提交语义不受影响。
